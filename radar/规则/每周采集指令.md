# 每周采集指令（给 Claude）

每周日晚上，在 Claude 桌面端里打开这个仓库，把下面这句话发给 Claude：

> 请按 `radar/规则/每周采集指令.md` 跑本周的采集。

以下是给 Claude 的指令正文。

---

你在帮我运行一个"信号雷达"。它每周从一批固定的公开来源里，按固定的取样方法收集信号，整理进数据文件，再由打分脚本统计。哪些方向值得做，要等信号积累多了，由脚本的统计和我的线下验证来判断，不是你这次的任务。

所以这件事最重要的一条是：**不预设方向**。你不知道、也不需要知道我关心什么行业或主题。你的工作是照着取样方法把每个来源过一遍，看到什么记什么。一个方向是靠很多独立来源里的信号自己"冒出来"的；如果你先有了想法再去找证据，找到的只会是你想找的东西，整个雷达就失去了意义。

## 必须遵守

1. 不要读仓库根目录的策划案，也不要读 `radar/周报/` 里以往周报的内容。里面有讨论过程中举过的例子，读了会让你先入为主。周报目录只看文件名，用来确定回看范围。
2. 不要用任何关键词搜索去找某个主题的材料：搜索引擎、站内搜索、平台的筛选框都不行。唯一的例外是来源清单的"取样方法"里明确写了固定关键词的来源。
3. 不修改 `radar/规则/` 目录下的任何文件。觉得规则有问题，写进最后的总结。
4. 每条信号必须来自你这次真正打开过的页面。链接填那个页面的地址，原文摘录逐字照抄页面上的原话，不超过 100 字，不改写、不概括。
5. `数据/信号.csv` 只能在末尾追加新行，不能修改或删除已有的行。`数据/验证.csv` 由我填，你不要动。
6. 所有"选项"类的字段，只能从 `radar/规则/打分规则.toml` 里列出的写法中选，一个字都不能差。拿不准就留空，写进总结，不要猜。
7. 只读不需要登录的公开页面，遵守网站的 robots 规则，同一个网站不要短时间内反复请求。遇到验证码或人机验证就停下，把这个来源记为"打不开"，不要尝试绕过，也不要换别的网站来顶替。
8. 来源清单里获取方式写着"我手动看""我手动查""我自己录入"的来源，你跳过。
9. 在我自己的电脑上运行时，不要执行 git commit，我会先看改动再自己提交。在云端会话里运行时，环境是临时的，跑完要提交并推送到这个会话自己的分支，不要推到 master，我在 GitHub 上看完再合并。

## 什么算一条信号

雷达找的是能赚钱的机会，所以每条信号都必须和钱有关。判断一条内容记不记，先过准入标准，再按类型填所属线和阶段。

### 准入标准：写得出"价值判断"才记

每条信号都要在"价值判断"一栏用一两句话写清楚三件事，写不出来就不记：

1. 谁：具体是哪一类人或企业。要写到能找到这群人的程度，比如"独立开发者""做跨境电商的小卖家""准备考证的上班族"，不能只写"用户""大家""企业"。
2. 什么需求：他们想解决什么问题、想要什么，以及这个需求为什么值钱：省时间、提效率、省钱、多赚钱，或者满足了一种以前没有的需求。
3. 钱在哪：已经有人在为它付钱；有明确的花费或损失；有能申请到的钱；或者你判断他们会持续愿意付钱的理由。

### 常见的有钱可赚的模式

下面这几种模式用来帮你判断一条内容有没有价值，不是让你去搜这些主题。不在这几种里的，只要过了准入标准，照样记。

- 新东西带出周边生意：某个新技术、新产品、新平台火了，很多人想用，但用不了、不会用、用不起或者不敢用，于是有人提供代注册、代部署、代搭建、中转、教程、课程、模板、配件、陪跑、外包等收费服务。这类周边生意本身就是最直接的信号。
- 新需求被满足：一个新产品解决了一个高频、持续的痛点；或者满足了一种以前没人意识到的需求，就像短视频出现之前，人们并没有碎片化娱乐的需求；或者开辟了一个全新的技术领域。
- 门槛带来服务需求：一项好处（补贴、资质、优惠、资金）需要申请，而申请有门槛，想申请的人就需要有人帮忙。
- 强制带来服务需求：一类企业被要求必须做某件事，不做会被罚，就会花钱找人做。
- 成本或损失：一类企业或个人的成本明显上升，或者出现了新的损失，并且已经在花钱应对。

### 各条线的具体要求

技术普及线（GitHub、Hacker News、Product Hunt、linux.do、掘金、模型和云厂商的公告等）：

- 单个新产品、新项目的发布，只有你分析后判断它属于下面三种之一时才记，并在"价值判断"里写明属于哪一种、理由是什么：满足了一类人高价值、持续性的痛点；发现了以前没被满足过的需求；开辟了全新的技术领域。普通工具、版本更新、小功能、个人练手项目、游戏移植、学术研究进展，不记。
- 围绕新技术出现的收费服务、教程、代做、付费社群，以及有人公开收入或付费人数的，都记，付费证据按下面的口径填。
- 有人求助、抱怨某件事做不到或者太贵，只有求助的人多，或者明显愿意花钱解决时才记。
- 大厂推出一键方案、同类产品融资，记"大厂进场"。这是判断机会窗口正在关闭的依据。

经营压力线（互动易和 e 互动、访谈等）：

- 只记一类具体的企业遇到的具体问题，并且能看到他们在为此花钱、准备花钱，或者损失有明确的数字。泛泛的"经营承压""行业周期波动""加强管理"不记。
- 国家统计局的数据不记成信号，只用来做第 6 步的行业压力表，给我做背景参考。

政策线：

- 主要记两种，"价值判断"里写清楚谁能申请、能拿到多少、门槛是什么：
  - 对企业有利、但有申请门槛的：需要申报的补贴、专项资金、资质认定、税收优惠、试点、奖励等；
  - 对个人有利、但有申请门槛的：需要申请的各类补贴、以旧换新、技能和创业补贴、人才政策等。
- 另外两种也记：有罚则的新强制义务，会让一类企业不得不花钱找人做；对某个新业态的明确放开或准入。
- 行业治理和安全监管、消费倡导、机构和人事、条例修订、规划和批复，如果不属于上面几种，不记。
- 只记中国大陆的政策。

### 明显无关、一律不记

纯学术和科研进展；模型发布本身（除非伴随明显降价或者开辟了新的能力领域，并且写得出谁会因此付钱）；娱乐和社会新闻；宏观统计数据；境外的政治、诉讼和监管动作；跟"谁付钱"无关的技术讨论。

### 宁缺毋滥

拿不准值不值得记的，先不记，但在最后的总结里列出最多 10 条你犹豫过的内容，附上链接和你犹豫的理由，由我来判断。我判断要记的，下次会告诉你。

### 过了准入标准以后，填所属线和阶段

| 类型 | 意思 | 记到哪条线、哪个阶段 |
|---|---|---|
| 新能力 | 出现了以前做不到的事，或者某件事的成本明显下降 | 技术普及线"新能力出现"；已经有很多人在用、在讨论的，记"开始普及" |
| 困难 | 一类企业或个人遇到的问题、成本、损失、风险，或者有人在反复求助 | 技术相关的记技术普及线"出现摩擦"；经营相关的记经营压力线"压力出现"，已经持续一段时间、被反复提到的，记"压力持续" |
| 花钱 | 有人在为某件事付钱：收费服务、课程、外包、岗位，或者企业披露在某件事上的投入 | 技术相关的记技术普及线"有人付钱"；经营相关的记经营压力线"开始花钱" |
| 规则变化 | 符合上面政策线要求的政策 | 政策线，"阶段"一栏填政策类型：发钱、加义务、撑腰、开窗、关窗 |

大厂推出一键方案、同类产品融资，记技术普及线"大厂进场"。

付费证据的口径：一个新产品上线、标了价格，本身不算付费证据，填"无"；能看到第三方围绕某个能力提供收费的服务、课程、代做，填"服务或课程上架"；能看到销量，或者有人公开了收入（比如 TrustMRR 上的数字），填"有销量或海外已验证收入"。

链接填条目自己的页面地址，方便我点开。如果你实际是通过列表页、RSS 或接口读到的，在备注里写上实际读取的地址。

政策类型的意思：

| 类型 | 意思 |
|---|---|
| 发钱 | 补贴、消费券、专项资金，通常带金额和申报期限 |
| 加义务 | 企业必须新做某件事，并且有罚则 |
| 撑腰 | 给中小企业或个人新的维权手段、议价筹码或保护 |
| 开窗 | 鼓励、放开某种新业态或新技术应用 |
| 关窗 | 禁止、整治、收紧，或者开始执法 |

## 开始之前

先读这几个文件：

- `radar/规则/打分规则.toml`：所有选项的合法写法。
- `radar/规则/来源清单.csv`：本周要过的是"一期"一栏为"是"的来源，每个来源按"取样方法"一栏取样。信号的"来源"一栏必须和这里的"名称"完全一致。
- `radar/规则/不碰的事.md`

`数据/信号.csv` 现在只看两样东西：已有的最大编号（用来接着编号），以及已有的链接和摘录（用来避免重复记）。先不要读 `数据/方向.csv`，它在第 3 步才用。

确定回看范围：看 `radar/周报/` 里最新一份周报的文件名（形如 `2026-W42.md`），回看起点是那一周之后的周一，终点是今天。如果还没有周报，回看最近 30 天。

## 步骤

### 1. 处理新的访谈和手动采样记录

`radar/访谈/` 和 `radar/数据/手动采样/` 下面，凡是还没有在 `信号.csv` 的"链接"或"备注"一栏出现过的文件（以下划线开头的模板文件除外），都是新的记录。手动采样记录里的每一条，来源填对应的平台（如"闲鱼淘宝和知识付费平台"），链接填条目自己的链接，没有的话填记录文件的路径，原文摘录照抄标题，价格、销量和记录文件的路径写进备注。以下是访谈的处理方法。

按上面的准入标准，把每份访谈里和钱有关的内容整理成信号：来源填"线下访谈"，链接填访谈文件的路径，原文摘录填对方的原话。访谈里提到每月花费或损失的，把金额折算成每月的人民币元数填进"金额元"，并在备注里写清楚怎么折算的。

### 2. 逐个来源取样

按来源清单的顺序，一个来源一个来源地过：

1. 按"取样方法"取出这个来源本次要看的全部条目。不多取，也不少取。
2. 逐条看，按上面的准入标准判断要不要记。
3. 记下这个来源一共看了多少条、记了多少条，最后写进总结。

每记一条信号，在 `信号.csv` 末尾追加一行：

- 编号：接着已有的最大编号往下编，格式 S0001、S0002……
- 价值判断：按准入标准写清楚谁、什么需求、钱在哪。这一栏空着的信号，打分脚本会直接忽略。
- 日期：信息本身的发布日期，格式 YYYY-MM-DD。页面上找不到日期的，填今天，并在备注里写"日期为发现日"。
- 付费证据：只有"花钱"类、并且和技术相关的信号才可能不是"无"。能看到有人上架了收费的服务或课程，填"服务或课程上架"；能看到销量，或者有人公开了收入，填"有销量或海外已验证收入"。
- 金额元：只有原文明确给出金额时才填，折算成每月的人民币元数，折算方法写进备注。
- 方向编号：这一步先全部留空。

同一个页面可以记多条信号，只要摘录不同。

取样方法里写了"和上次相比"的来源（价格页、TrustMRR 等），每次把页面的正文存一份快照到 `radar/数据/快照/来源名称/YYYY-MM-DD.md`，再和这个目录下最近一次的快照比较。第一次没有快照可比的，只存快照，不记变化。

### 3. 把信号归到方向下

采集全部完成以后，再读 `数据/方向.csv`。

方向由三件事确定：什么新能力或什么困难、影响谁、他们遇到了什么问题。

- 新信号和已有方向对得上的，在"方向编号"一栏填那个方向的编号。这一步是唯一允许修改你本次新加的行的地方。
- 对不上的信号，如果本次有至少两条、并且来自至少两个不同来源的信号指向同一件事，就提议一个新方向：编号接着往下编（D001、D002……），状态填"待确认"，类型填"快钱"或"长钱"（技术普及线为主的是快钱，经营压力线为主的是长钱）。
- 提议的方向必须填好"付费方"和"要解决的问题"两栏："付费方"写到具体的一类人或企业，"要解决的问题"写一句话。付费方不同的，即使技术相同，也要分成不同的方向。写不清付费方的，不要提议。
- 方向要等我确认，把状态改成"观察中"以后才参与打分。我否掉的会改成"否决"，不要再提议同样的方向。
- 其余信号的方向编号留空。孤零零的一条信号不是方向，等以后有别的来源出现同类信号再说。

"窗口剩余"一栏一般不用填，脚本会看方向下有没有"大厂进场"的信号自动判断。只有当方向下已经有"大厂进场"的信号时，才需要按那条信号选"同赛道融资"或"云厂商一键方案"。

新建或更新方向时，其他各个分项只能从规则里的选项中选，每选一项都要在对应的"依据"一栏写明理由并引用信号编号，例如"见 S0012：受访者说每月在这件事上花约两万元人力"。依据只能来自已经记下的信号和访谈，不要为了填分项再去搜索。没有依据的分项留空，留空的方向会在周报里列出来，由我去线下补。已有方向的分项，只有出现新依据时才改，改了要写进总结。"状态"一栏除了提议时填"待确认"，其他时候不要改。

### 4. 检查不碰的事

对每个新建或更新的方向，对照 `不碰的事.md` 检查一遍。没有命中就在"命中不碰"一栏填"否"；命中了就填"第几条：理由"。同时填好"准入成本"和"准入成本依据"。

"用不了"类的需求按 `不碰的事.md` 第一条的说明处理。

### 5. 更新政策

规则变化类的信号里，凡是一份正式的政策文件或征求意见稿，同时在 `政策.csv` 里加一行，编号接着往下编（P001、P002……）。已有政策推进到了新阶段（比如从征求意见到正式发布），用同一个编号再加一行，填新的阶段和更新日期，不要改旧的那一行。阶段只能往前走。一条政策可以属于多个类型，用顿号隔开。

### 6. 每月第一个周日，额外做一件事

如果今天是本月第一个周日，或者本月第一个周日已经过了、`radar/周报/` 里还没有本月的行业压力表，就做这一步。

打开国家统计局最新一期"规模以上工业企业利润"的发布，找到分行业的主要财务指标表，把**所有行业**的营业收入、营业成本、利润总额三项累计增速，连同上一期的利润总额增速，原样抄进 `radar/周报/YYYY-MM-行业压力.md` 的一张表里，附上两期发布的链接。然后按 `打分规则.toml` 里"行业压力"一节的规则，逐个行业判断是否满足条件，在表里标出来。这张表只给我做背景参考，不记成信号。

不要挑行业，不要改规则，也不要换别的指标。数据找不到或者口径对不上，写进总结。

### 7. 检查并生成周报

在仓库根目录运行：

```
python3 radar/规则/score.py --check
```

如果报出的问题出在你本次新加的行上，就改正那几行。之前就存在的问题不要动，写进总结。然后运行：

```
python3 radar/规则/score.py --since 回看起点
```

`回看起点` 换成你在"开始之前"确定的日期，格式 YYYY-MM-DD。

### 8. 最后给我一份简短总结

包括：

- 一张表：每个来源看了多少条、记了多少条、有没有打不开，打不开的原因；
- 提议了哪些新方向，每个方向写清付费方、要解决的问题、依据的信号编号，等我确认；
- 改了哪些已有方向的哪些分项；
- 你犹豫过、最后没记的内容，最多 10 条，附链接和理由；
- 哪些已记的信号或分项你拿不准；
- 有没有可能命中"不碰的事"的方向；
- 你觉得规则或取样方法有什么需要我调整的地方。

总结里不要写你对哪个方向更看好，那是我的事。
